## Architecture

Next.js **16.2.10** (App Router) with React 19, TypeScript (strict), and Tailwind CSS v4.

- All source lives under `src/`: routes in `src/app/`, shared components in `src/components/`, data/logic in `src/lib/`. Path alias `@/*` maps to `src/`.
- **Routes**: `/` (Omnibar hero + trending), `/laptops` (browse: search + brand filter + price sort + grid/list view toggle), `/laptops/[id]` (bento-grid details; `params` is a Promise — `await` it; fetches from the backend and 404s via `notFound()` on API 404/422), `/wizard` (6-step needs wizard), `/chat` (Pico chat interface — results/comparison happen inline here), `/compare`, `/saved` (live wishlist listing: search-within-saved + grid/list toggle + remove hearts; signed-out visitors get a sign-in prompt rather than a redirect), `/login` (merged sign-in/create-account tabs), `/about` + `/faq` (static marketing/help pages, linked from the footer; FAQ uses the shadcn accordion). `/results` and `/signup` are thin redirects to `/chat` and `/login` respectively — kept so old links don't 404.
- **PickScore modes across surfaces**: everything server-rendered or agent-produced is general-mode; personalization is a client-side overlay for signed-in users with wizard preferences (`hasPreferences === true`), always via `POST /laptops/calculate-score[/batch]` and only applied when the response says `mode: "personalized"`. Three surfaces: the details-page `PickScoreCard` "For you" tab (last tab, auto-selected, indeterminate progress placeholder while computing — `components/pick-score-card.tsx`), the details hero ring (`components/personal-pick-score-ring.tsx` — falls back to the best-fit use-case score until the personal one resolves), and the chat shortlist rings (batch overlay in `chat/page.tsx` with a person badge + explainer note). Pico's reply *text* still cites general-mode scores — a known, accepted mismatch with the personalized rings.
- **Laptop data comes from two places.** Live pages (`/laptops`, `/laptops/[id]`) are Server Components that fetch via `src/lib/api/` (`client.ts` fetch wrapper, `types.ts` backend shapes, `adapters.ts` `mapBackendLaptop`). The adapter fills `Laptop` fields with no backend source yet (score, radar, xaiFactors, sentiment, …) with neutral placeholders — only safe for views that don't render them (browse uses `showScore={false}`); read the adapter comment before reusing it. `src/lib/laptops.ts` keeps the `Laptop` type and six mock laptops used by home/trending, chat, and compare. Backend `image_urls[]` maps to `images` (all photos) and `image` (first photo); mocks omit `images`, so consumers fall back to `[image]`. Note: scraped Apple `image_urls` include both screen-size variants from shared specs pages (13″+15″, 14″+16″), so galleries show look-alike pairs — a backend scraper issue, not a frontend bug.
- The `/laptops` brand chips come from `GET /brands` filtered to `is_active`, passed into `LaptopsBrowse` as a `brands` prop — *not* derived from the rows on the page, so an active brand whose laptops aren't processed yet still gets a chip (it renders the empty state until they are). The component unions that list with the brands actually present, so a laptop whose brand was later deactivated stays reachable.
- **`/laptops` browse state lives in the URL, server-rendered per query.** `page.tsx` reads `searchParams` (a Promise in Next 16 — await it) for `q`/`brand`/`sort`/`min`/`max`/`page`/`view`, calls `GET /laptops/` with the matching params, and passes one page of results to the client component. `laptops-browse.tsx` is presentation only: every control writes to the URL via `router.push` inside `useTransition` (the previous page stays dimmed rather than blanking), and there is no client-side filter/sort/slice left — with pagination those would act only on the 24 rows on screen, so the count and pager would disagree with what is shown. Filtered views are shareable and the back button works. It previously fetched all ~277 rows (~700 KB) and filtered client-side with an IntersectionObserver batch renderer; that is gone.
- **Never import a plain value from a `"use client"` module into a Server Component.** Only components survive the RSC boundary intact; a plain export becomes a client-reference stub. `SORT_ORDERS.includes` threw "is not a function" at request time until the shared constants moved to `app/laptops/browse-params.ts`, a neutral module both sides import.
- Most pages are client components (`"use client"`) because they hold interactive state (wizard steps, chat pro-tuning sliders/compare checkboxes, browse filters, compare tech-row toggle, auth tabs). `components/charts/*` (recharts), `theme-toggle`/`theme-provider` (next-themes) stay isolated client leaves.
- `src/app/layout.tsx` wraps all pages in ThemeProvider (next-themes, class strategy) + Header + Footer. Dark mode is toggled via the `.dark` class; `suppressHydrationWarning` on `<html>` is required.
- **The logo is `components/brand-mark.tsx`, inlined on purpose.** Source artwork and the spec sheet live in `public/PickWise Logo/` (master, micro, lockup); the component must stay geometrically identical to them. It is inlined rather than loaded through `next/image` because the artwork is drawn in `currentColor`, so one component covers navy-on-light (`text-brand`), white-on-navy (inherited, e.g. the login panel) and the dark theme's lighter tint — an SVG referenced through `<img>` is a separate document that inherits nothing and renders black. Two cuts: `master`, and `micro` (fatter strokes, tighter box) for under 24px; never render either below 16px. It is `aria-hidden` since every placement sits beside the "PickWise" wordmark as real text. The header composes mark + live text rather than shipping `pickwise-lockup.svg`, so the wordmark uses the page font and stays selectable; that lockup file is for external use and its `<text>` still needs outlining first.
- **Browser icons** (`src/app/`): `icon.svg` is the white mark on a transparent ground, `favicon.ico` is built from the same artwork (16/32 micro, 48 master) so the fallback doesn't show a different icon than the SVG, and `apple-icon.png` keeps a navy tile because iOS composites transparency in a home-screen icon against black. All three carry explicit hex, not `currentColor` — an icon is fetched as its own document with no page CSS, so `currentColor` resolves to black. Next's `apple-icon` convention takes no SVG, hence the PNG.
- `components/laptop-card.tsx` is shared by home/browse (`showScore={false}`, compact) and chat results (`showScore` default true — adds `XaiPopover` + plain-English panel + optional compare checkbox via `compareChecked`/`onCompareChange`). `layout` prop: `"grid"` (default, vertical) or `"list"` (horizontal row, image column left — used by the browse list view). The image area is an embla carousel (`ui/carousel.tsx`) with `CarouselDots` — a custom addition to the shadcn component: sliding window of max 3 dots, hidden for single-image laptops, glass-pill styling passed in from the card. Swipe is intentionally blocked by the stretched-link overlay (z-10) that makes the whole card open the details page; the dots (z-20) are the navigation.
- `components/laptop-gallery.tsx` is the details-page client gallery: selectable thumbnails (one per image, wraps) driving the hero photo.
- **Product photo conventions**: photo panels (card image area, details gallery) use `bg-white` in both themes so transparent-background PNGs read cleanly; photos keep `mix-blend-multiply dark:mix-blend-normal` (multiply is a no-op on white in light mode, normal shows the photo plainly on white in dark mode) — keep both when adding images. Card photos use `object-contain` (no cropping), not `object-cover`.
- **Apple photos are upgraded to their 2x twin** (`src/lib/api/image-urls.ts`, applied in both adapters). Apple's scraped sources come off the spec sheet, where `_large.jpg` means the 1x variant of a thumbnail — measured, 245×148 at 7 KB, against a ~380×300 card slot. `next/image` cannot fix that: the optimizer never upscales past a source's intrinsic width, so `quality`/`sizes`/`deviceSizes` are irrelevant to blur. Apple publishes `_large_2x` (490×296) for every one of them; all 61 distinct URLs in the catalog were checked and every rewrite resolves 200. ASUS (2400×2400) and Acer (1000–1619px) need nothing. This is a stopgap for a backend fix: the Apple scraper reads `/specs/`, so the images are illustrations (`chip_m4`, `ports_back_mx`, `in_the_box`) rather than product photography, and whichever lands first becomes a card's hero.
- **Cards pass `sizes`.** `laptop-card.tsx` keys it off the `layout` prop (grid `400px/50vw/100vw`, list `256px/160px`). Without it the optimizer only offers 640w and 1280w, so the list view's 160px image column is handed a 1280w render of a multi-MB ASUS original.
- Remote images (Unsplash, pravatar, apple.com, ASUS CDN, Acer's `static-ecapac.acer.com`, YouTube channel avatars) are allowlisted in `next.config.ts` `images.remotePatterns` — scraped image hosts must be added there or `next/image` throws. `next.config.ts` is read at boot, so adding one needs a dev-server restart.

## Styling

- shadcn/ui (base-nova style, base-ui primitives — `render` prop instead of Radix's `asChild`) is configured via `components.json`; generated components go in `src/components/ui/`. Add components with `npx shadcn add <name>`.
- Interactive primitives use the official shadcn components restyled via className overrides (twMerge resolves conflicts — later classes win): dropdown-menu (header account menu, conversation action menu), popover (XAI popover, birthday date picker with calendar), dialog (review-source modal, conversation rename), tabs (login), input (all text inputs), textarea (chat composer — native `field-sizing-content` auto-grow), checkbox (compare), avatar (user avatar — initial as direct child, not AvatarFallback, so it inherits the caller's font size), badge (laptop-card tag/spec chips), progress (personal-PickScore placeholder, indeterminate via `animate-progress-slide`), message-scroller (chat thread), accordion (FAQ page), card/empty/field/spinner/separator/sidebar (admin), plus the earlier button/select/sheet/carousel/navigation-menu. Don't hand-roll popovers/modals/menus/tabs. Domain visuals (GlassSurface, PickScoreRing, charts) stay custom — no shadcn equivalent.
- Six generated files carry deliberate local additions that `npx shadcn add --overwrite` would destroy: `ui/carousel.tsx` (`CarouselDots`), `ui/dialog.tsx` (`overlayClassName` prop on DialogContent, used by the review modal's darker backdrop), `ui/accordion.tsx` (open/close animations gated behind `motion-safe:`; the matching `accordion-down/up` keyframes live in `globals.css`), `ui/alert.tsx` (`success`/`warning`/`error`/`info` variants on the app's `positive`/`warning`/`negative`/`brand` tokens, used by admin job-result banners via `app/admin/admin-outcome-alert.tsx`), `ui/spinner.tsx` (`motion-safe:` gate on its `animate-spin`), `ui/skeleton.tsx` (same gate on its `animate-pulse`), and `ui/button.tsx` (see the button section below).
- **Buttons: two radius languages, one component.** `ui/button.tsx` adds a `shape` axis (`default` | `pill`) orthogonal to `variant` and `size`, plus `xl`/`2xl` sizes for marketing-scale CTAs and `soft`/`tint` variants on `--surface-2`/`--brand-tint`. Public pages use `shape="pill"`; the admin portal uses the default `rounded-lg`. Don't mix the two within one surface. `secondary` is not a substitute for `soft` — `--secondary` and `--surface-2` are near-identical in light mode but diverge hard in dark. Pill horizontal padding comes from `compoundVariants` (round ends eat optical space beside the label), so a pill's `px` is set by its size, not by an override.
- **Never hand-roll a button.** A bare `<button className="px-… py-… rounded-…">` silently loses the `active:translate-y-px` press feedback, the `focus-visible` ring, and `disabled:` styling. Six public CTAs drifted this way (six different paddings, three radii) before being migrated onto `Button`.
- **A `Button` that renders a link needs `nativeButton={false}`.** `render={<Link … />}` swaps the `<button>` for an anchor, but base-ui still assumes a native button and warns about the lost semantics at runtime. Same for any base-ui component with the prop. Note when auditing this: a regex from `<Button` to the first `>` stops at the nested `<Link />`'s own `>`, so it misses a `nativeButton` on a later line and reports false positives — match with tag-depth tracking.
- **Button spacing scale** (follow it): `gap-1` icon-button clusters in table rows, `gap-3` every button/control row (action pairs *and* filter bars), `gap-4` page-level section stacks. Action rows generally take no margin of their own — they sit in a parent `flex flex-col gap-4`. Action pairs were `gap-2` until measured on screen: 8px between buttons against the 6px icon-to-label gap *inside* a button is only a 1.33× step, so the pair grouped as one blob. 12px gives the ~2× step proximity needs, and matches what the public hero pair already shipped.
- **Icons inside shadcn components carry no sizing classes** — Button/Badge/DropdownMenuItem/Sidebar size their own svgs (`[&_svg:not([class*='size-'])]:size-4`, tightened per `size` variant), and a `size-*` class silently opts out of that. In a Button, an icon next to a label takes `data-icon="inline-start"` (or `inline-end`) so the button's asymmetric padding rule applies; icon-only buttons take nothing. `data-icon` is only read by button/badge/tabs — elsewhere the icon is a bare `<Icon />`.
- **Casing: Title Case for headings, sentence case for everything else.** Page titles (`AdminPageHeader title`), the breadcrumbs and sidebar labels that mirror them, and `<h1>`/`<h2>` section headings are Title Case, with articles, coordinating conjunctions and short prepositions left lowercase ("Waiting on You", "Still Waiting for a Page", "PickScore by Use Case"). Everything else stays sentence case: button labels, empty states (`AdminEmptyState title` is a sentence, not a title — "No laptops match"), alerts, body copy, job-type labels, and hero/marketing headlines that are full sentences or questions ("Which laptop is right for you?").
- **Admin conventions** (`src/app/admin/`): panels and table containers are `Card` (`className="py-0"` for table cards, `gap-0 p-4` for padded blocks); the three list states come from `admin-states.tsx` (`AdminLoadingState`, `AdminEmptyState`, `AdminErrorState` — the latter two build on `ui/empty.tsx`); the dashboard uses a layout-matching skeleton instead (`dashboard-skeleton.tsx`) because it blocks on ten parallel requests, where a spinner says only "wait" — its `Line` helper puts each placeholder bar in a box the height of the text line it replaces, since sizing the bar alone left the skeleton ~44px short and the page jumped when data landed; dialog forms are `FieldGroup` + `Field` + `FieldLabel`, not hand-rolled `<label>` stacks; job results are `OutcomeAlert` (`admin-outcome-alert.tsx`). The admin shell is the shadcn `Sidebar` (`admin-shell.tsx`, `collapsible="icon"`, state persisted in the `sidebar_state` cookie read by `admin/layout.tsx`); its `SidebarTrigger` lives in `admin-topbar.tsx`, not inside the sidebar, so it stays reachable when collapsed and on mobile (where the sidebar renders as a Sheet).
- **Admin listing state lives in the URL, via `admin-query-state.ts`.** `useAdminQuery({ filters, sortKeys, defaultSort })` is the one source of filter/sort/page state on all ten listing screens — it reads `useSearchParams`, and `set`/`setPage`/`sortBy` write back. Values equal to their default are omitted, so an untouched screen keeps a clean address. Writes use `replace`, not `push`: these are refinements of one screen, and pushing would bury the way out of the page under a history entry per pager click and per debounced keystroke. `set` resets to page 1 (page 3 of a narrower result set shows an empty table); pass `{ resetPage: false }` only for a control that refines rows already on screen, as `/admin/queue`'s in-page search does. Sort keys are validated against the screen's own `sortKeys` because most screens forward the key to the API as an ORDER BY column and the URL is user-editable. Text inputs pair it with `useSearchDraft(committed, commit)` — the draft leads and the URL follows on a 300ms debounce, since a router write per keystroke would make typing lag. It replaced ten hand-rolled copies of the same `filterSig`/`paramsSig` pair; `query.signature` is now the stale-row guard (append `reloadTick` where a screen has one). Screens must destructure primitives out of `query.values` for effect deps — the `values` object is rebuilt each render, while `sort` is memoised and safe as a dep.
- **`useSearchParams` needs a Suspense boundary, and there is exactly one** — in `admin-shell.tsx` around `{children}` in the `SidebarInset`. A production build fails on a prerendered page that calls it unwrapped, so this covers every listing screen at once while the sidebar and topbar keep prerendering around it. Don't add per-page boundaries.
- **Admin breadcrumbs are derived, not typed.** `AdminPageHeader` builds its trail from the sidebar config via `adminCrumbsFor(pathname)`, so a page's crumbs are always `Dashboard › <nav group> › <nav label>` — the words the admin actually clicked. Pages pass no crumb list; only levels *below* a nav entry (the laptop create/edit forms) pass `trail={[…]}`. Group crumbs stay plain text because `/admin/catalog`, `/admin/benchmarks` and `/admin/reviews` are redirects into their first child, so a link there would land somewhere other than what the crumb names; the nav entry above a `trail` becomes a link. The nav config lives in `admin-nav.ts` rather than `admin-shell.tsx` because that file is `"use client"` and the laptop create/edit pages are Server Components. Hand-typed crumbs drifted on 11 of 21 screens before this (wrong group after Brands moved to Collect, pre-rename labels, and `/admin` rendering "Dashboard › Dashboard").
- **A screen's page title is its nav label.** `AdminPageHeader title` matches the `admin-nav.ts` label that leads to it, so the crumb, the sidebar entry and the `<h1>` all say the same word. Seven screens disagreed before this; the nav wording won on six (Customizations → Upgrade Options, Review Channels → Sources, Raw Reviews → Match Queue, Agent → Chatbot Monitoring, Taxonomy → Tags & Taxonomy, Customer Questionnaire → Questionnaire) and the seventh went the other way: `/admin/reviews/pipeline` was labelled "Aggregate", but aggregation is only the last of that page's three sections (Ingest → Process → Aggregate), so naming the page after it would both clash with the section heading and hide the other two runs. When a rename can't satisfy both, rename the nav.
- **Admin footer** (`admin-footer.tsx`, rendered in `SidebarInset` after the content): copyright plus the backend host the portal is pointed at, read from `API_BASE_URL`. It is not the storefront `Footer` — those link columns are customer navigation, and "Back to site" already lives once in the `SidebarFooter`. The API host earns its place because this portal launches scrapes, processor runs and deletes against live data, so "am I about to do this to production?" should be answerable without devtools. No build/version stamp: nothing plumbs one through, and inventing one is fake precision.
- **The admin nav is ordered by the pipeline, not by domain** — the groups in `admin-shell.tsx` follow the four stages in the backend's `admin.md` §2 (Collect → Catalog → Rank & search → Reviews), then the non-pipeline groups. Brands leads Collect because `is_active` and `base_scrape_url` are what the crawler reads. Keep new screens in stage order.
- **Each pipeline action has exactly one home.** `/admin/pipeline` ("Raw records") is a read-only table: it used to start bulk scrapes and processor runs too, duplicating `/admin/queue` and `/admin/processing` with a hardcoded batch of 100 against their 1–1500, so the same job could be launched twice at an unshown limit. Scraping lives on `/admin/queue`, processing/tagging on `/admin/processing`. Don't add action buttons back to a listing screen.
- **Background runs return 202 with a job to poll.** Five job types are recorded in `background_jobs` (`processor.process_pending`, `processor.categorize_untagged`, `scraper.bulk_scrape`, `scraper.scrape_targets`, `embeddings.generate_all`) and are followed with `useJob` + `AdminJobPanel`. Embeddings joined this in Aug 2026; before that it kept no job record, so `/admin/embeddings` had to baseline the embedded count and infer a stall from a count that stopped moving — that hook is gone, replaced by `useEmbeddingStatus`, which now only reports overall coverage (the one thing a job can't answer, since it knows only its own run). PickScore `generate-all` still writes no job row.
- **Acer pages are captured by script, not Ctrl+S** (`/admin/upload`). Chrome's Save Page writes the rendered DOM, and Magento's gallery script deletes the `x-magento-init` block holding the image list as soon as it runs — such a save parses fine but arrives with 1–2 photos instead of 9–13. `upload/console-snippet.tsx` is the copy-paste console script that re-fetches `location.href` same-origin (carrying the WAF's validated `_abck` cookie) and downloads the original response. It takes no URL list on purpose — an earlier version baked the queue in and went stale. It can't POST directly: the API's CORS allowlist doesn't include store.acer.com. The "Still waiting for a page" list queries `pending` **and** `failed` targets (two calls merged, since `GET /scraper/targets` takes one status) — `failed` alone hid every newly crawled product until a pointless scrape had run.
- **Two write paths need the UI to guard what the API doesn't.** `/admin/catalog/customizations` creates via `POST /customizations/` (explicit laptop ids) or `POST /customizations/bulk-by-pattern`; the pattern route matches with SQLAlchemy `.contains()`, which compiles to `LIKE`, not `ILIKE`, so matching is **case-sensitive** and the form warns about capitalization. `add-options-dialog.tsx` previews the matches via `GET /customizations/bulk-by-pattern/preview`, which shares the write's exact predicate (`_laptops_matching_pattern` in the backend's `customization_router.py`) — the preview used to re-derive that test client-side over the whole downloaded catalog, which meant a second copy of the predicate kept in sync by hand. Submit is blocked while the debounced preview is still catching up, so it can never fire against a stale match list. Neither route de-duplicates, so the form says so. Likewise `POST /reviews/process/{id}` (the Match Queue's per-row summarize) has neither of `process-bulk`'s guards: it 400s unless the review is `matched` (so the menu item is disabled ahead of the error), and nothing skips a video that already has chunks — bulk filters those out of its candidate list instead, so a re-run here stores a second copy. It also blocks for a minute or more.
- `useJob(token, onFinished?)` — the completion callback fires once per job from the poll that first sees it stop. Use it to refresh a list after a run; the "adjust state during render" trick is only legal for a component's **own** state, and calling a parent's setter that way throws "Cannot update a component while rendering a different component".
- Tailwind v4 is configured in CSS, not JavaScript: there is no `tailwind.config.*` file. Theme customization goes in `src/app/globals.css` via `@theme`; the PostCSS plugin is `@tailwindcss/postcss`. Use theme tokens rather than hardcoded palette colors — both the original shadcn set (`bg-background`, `text-muted-foreground`, `bg-primary`, …) and the additive glassmorphism set (`bg-surface`, `bg-surface-2`, `bg-brand`/`bg-brand-tint`, `text-positive`/`text-negative`, `border-line`, plus the raw CSS vars `--glass`/`--glass-edge`/`--shadow` for backdrop/shadow work).
- **Glass surfaces**: use `components/glass-surface.tsx` (plain CSS glassmorphism — translucent fill + `backdrop-filter: blur(20px) saturate(180%)` + inner-edge highlight border) for the app's floating/overlay layers only — nav island, chat composer, XAI popover, account menu, sticky compare header, review modal. Never wrap body-level/flat content in it, and never nest one inside another. Don't reach for a third-party glass/liquid-glass package here — an earlier attempt with `liquid-glass-react` broke in-flow layout (it bakes in a self-centering `translate(-50%, -50%)` transform and several `position: relative` decorative sibling elements meant for a single floating button, which inflated container heights and misplaced content) and caused SSR/client hydration mismatches once wired to theme state. Plain CSS has none of those problems.
- Animations are `@theme` tokens in `globals.css` (`animate-fade-in-up`, `animate-float`, `animate-shimmer`, `animate-bounce-dot`, `animate-token-in`, `animate-progress-slide`). Always gate animations behind the `motion-safe:` variant. Card grids stagger entrances via inline `animationDelay`. `animate-token-in` is the streamed-word fade in chat: opacity-only (transforms don't apply to inline boxes), applied to per-word spans with stable index keys so appended text only animates the newly mounted words.
- Chart colors are dataviz-validated (CVD-safe, contrast-checked) — radar pair `#3b6db4`/`#9333ea`, price-history and admin-trend pair `#3b6db4`/`#c2571b` (second series dashed, exported as `TREND_COLORS`); single-series charts use `#3b6db4` alone. Charts read surface colors from CSS vars (`var(--border)` etc.) so they follow the theme. **A success/failure series is blue-and-orange, not green-and-red**: the `--positive`/`--negative` pair fails the dark-mode lightness band and only reaches the 6–8 CVD floor band, while the documented pair passes all six checks in both modes (re-check with the dataviz skill's `validate_palette.js` before introducing any new pair). Marker rings take `var(--card)`, not `var(--surface)` — the two diverge in dark mode, and every chart sits on a `Card`.
- **Admin trend charts** (`components/charts/trend-line.tsx` + `lib/daily-series.ts`): day-over-day lines on `/admin/agent-monitoring` (turns per day, error rate, median vs 95th-percentile latency), `/admin/jobs` (items succeeded vs failed, every job type) and `/admin/embeddings` (the same chart scoped to `embeddings.generate_all`). The last two are one shared component, `admin/admin-job-trend.tsx` — it charts *items*, not runs, because one run can carry 1500 of them. Rules they exist to keep: each chart fetches its **own unfiltered** page of rows, so the filter bar beneath never reshapes the trend; the axis is **dense** (days with no rows are plotted, or a quiet week draws as a straight line through it) but **never extends past the oldest fetched row**, since the fetch is capped (1000 runs, 200 jobs) and zeros for unfetched days would read as "no traffic" instead of "not loaded"; when the cap was hit, the oldest day is **also dropped** — it holds only the rows that fit, so it would plot as a real dip; and a day with no rows plots `null`, not 0, because a 0% error rate and 0ms latency both look like a good day. Volume, rate and duration are three scales, so they are three charts — never a second y-axis.
- **Coverage history** (`admin/embeddings/coverage-history-card.tsx`, `GET /embeddings/laptops/coverage-history`): two cumulative lines on `/admin/embeddings` — laptops in the catalog against laptops that are embedded. Unlike the job charts it arrives **pre-bucketed from the server** (cumulative totals need every laptop row, not a page), so days are used as given, never re-bucketed locally — render the `YYYY-MM-DD` keys with `formatDayKey`, since `new Date("2026-08-10")` is UTC midnight and prints the previous day in a negative-offset zone. It is bucketed by `Laptop.created_at` and counts "has a vector *now*", which makes it a **cohort** chart, not a work log: the right-edge gap is today's missing count, and a gap opening further back is a backlog no run cleared. Bucketing by the embedding's own timestamp was rejected — `LaptopEmbedding` has only `updated_at` and `upsert_laptop_embedding` overwrites it, so one re-run would restamp every row and flatten history into a single vertical jump. When coverage is healthy the two lines overlap; that is the good state, not a rendering fault.
- **Timeframe control**: `admin/admin-trend-range.tsx` (7/14/30/90 days, default 14). It **re-buckets the already-fetched window rather than refetching**, so switching is instant and the chart can never disagree with the numbers beside it; the cost is that a long range can outrun the window, which is what the axis-shortening and the "older history isn't charted" caption above exist to handle. `/admin/agent-monitoring` gives all three charts one shared control — separate pickers would let the page show volume and latency over different periods and invite a false comparison. `TrendLine` drops its point markers past 31 points: the spec floor is r≥4, and at 90 days that many dots merge into a rope, so they go rather than shrink.
- Prices, scores, and other data numbers use the `tabular-nums` utility class for column alignment.

## Auth

Live against the backend's JWT bearer auth. `src/lib/auth-context.tsx` (`useAuth`) owns the session: token in localStorage (`pickwise_token`), trusted only after `GET /auth/me/profile` succeeds; login is OAuth2 form-encoded (`username` field accepts username or email), plus Google sign-in via GIS ID token. `src/lib/api/auth.ts` has the API surface (profile, preferences, avatar). `/login` is the tabbed sign-in/create-account page; registration requires email verification before login works. `/profile` and `/wizard` are auth-gated client-side (redirect to `/login`).

`/login`'s form panel leads with the Google button, then a divider, then the email form — one tap beats three fields plus an email round-trip on register, and both tabs share the panel. The divider names the path *below* it ("or sign in with email" / "or sign up with email"), so it has to be reworded if that order ever flips back. Notice/error banners stay above both, since Google and the form write to the same `error` state. The GIS container keeps `[color-scheme:light]`: when the embedder's scheme differs from the iframe's, Chromium paints an opaque backdrop behind the pill.

The auth context also tracks `hasPreferences` (fetched from `GET /auth/me/preferences` per session, `null` = signed out/unknown): the header hides the "Needs Wizard" nav entry once it's `true` — after completing the wizard, preference updates happen via the account menu's "Preferences" item → the profile page's "Laptop preferences" card, which links back to `/wizard`. The wizard flips the flag via `markPreferencesSaved()` on save.
